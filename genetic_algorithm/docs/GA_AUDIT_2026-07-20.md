# GA-Systemaudit vom 20.07.2026

Status: belastbare Arbeitsgrundlage für Reparatur und Redesign. Dieses Dokument ersetzt keine
Live-Freigabe. Während des Audits wurden weder laufende Waves noch bestehende Konfigurationen,
Registry-, Corpus-, Modell- oder Ergebnisartefakte verändert.

## Kurzentscheidung

Eine vollautomatische Folge-Wave sollte auf dem aktuellen System **noch nicht** gestartet werden.
Zuerst müssen Messung, Holdout-Semantik, Run-Lifecycle und Ergebnisvertrag zuverlässig werden.
Andernfalls automatisieren wir nicht die Verbesserung, sondern verstärken Messfehler, stille
Config-Fehler und inkonsistente Zustände.

Die sinnvollste Reihenfolge ist:

1. Cache-, Resultat-, Unit- und Reproduzierbarkeitsfehler beheben.
2. Einen kanonischen Runner mit transaktionalem Lifecycle und isolierten Artefakten schaffen.
3. Holdout, Pair-Validation, NSGA-II und Parallel/Sequential-Parität korrigieren.
4. Die neue Evaluationslogik im Shadow-Modus gegen vorhandene Strategien replayen.
5. Erst dann einen deterministischen Next-Wave-Planner zunächst mit manueller Freigabe betreiben.

Die zugehörigen Zielbilder stehen in
[GA_EVALUATION_SPEC.md](GA_EVALUATION_SPEC.md) und
[NEXT_WAVE_AUTOMATION_PLAN.md](NEXT_WAVE_AUTOMATION_PLAN.md). Umsetzbare Arbeitspakete stehen in
[GA_TODO.md](GA_TODO.md).

## Umfang und Methode

Untersucht wurden die aktiven und konkurrierenden Laufpfade unter `genetic_algorithm/`, die
Top-Level-Launcher und Generatoren, Konfigurationsschema und Validator, Fitness/Backtest/Cache,
Standard-, Island- und Generic-Island-Evolution, Robustheitsfeatures, SIS, Registry/Scheduler,
Tracker/Hall-of-Fame sowie vorhandene Resultate und der Strategy-Corpus.

- 238 Python-Dateien außerhalb generierter `data/`- und `output/`-Bäume
- ungefähr 87.355 Python-Codezeilen in diesem Scope
- 46 `test_*.py`-Dateien
- statischer Import-/Compile-Check erfolgreich
- Gesamtsuite: 1.174 Tests bestanden; 6 Collection-Fehler in manuellen LLM-Provider-Skripten,
  deren Funktionen irrtümlich als Pytest-Tests mit nicht existierenden Fixtures gesammelt werden
- separater Orchestration-Lauf: 57 bestanden, 2 fehlgeschlagen
- separater Robustheit/SIS-Lauf: 343 bestanden, 1 fehlgeschlagen, 3 übersprungen
- 278 fokussierte Evaluations-/NSGA-/Robustheitstests bestanden; wichtige End-to-End-Invarianten
  fehlen trotzdem

Es wurden keine teuren neuen Freqtrade-Backtests ausgeführt. Aussagen zu Wirksamkeit beruhen daher
auf Quellcode, vorhandenen Artefakten und vorhandenen A/B-Läufen. Beobachtete Zusammenhänge werden
ausdrücklich nicht als kausaler Beweis ausgegeben.

## Tatsächliche Architektur

Der aktuell sichtbare Hauptpfad ist:

```text
Wave-Generatoren
  -> YAML in config/queue
  -> ga_auto_queue_v2.sh / weitere Launcher
  -> YAML vor dem Start nach config/done
  -> python -m genetic_algorithm run
  -> CLI-eigene Registrierung
  -> Standard | Island | Generic-Island
  -> FitnessEvaluator -> DirectBacktester -> Cache
  -> Tracker / HOF / Checkpoints / globale Diagnostics / registry.json
```

Daneben bestehen zwei semantisch andere Wege:

```text
run_ga.py
  -> zusätzlicher Preflight, Post-Processing, Export und Summary

python -m genetic_algorithm queue add
  -> Registry -> Python-Scheduler -> python -m genetic_algorithm run
```

Damit gibt es derzeit keinen eindeutigen Owner für Run-ID, Status, Retry, Resultat oder Artefakt.
Auch die Dokumentation bildet diese Drift nicht ab: `docs/INDEX.md` bezeichnet mehrere Features als
vollständig, obwohl aktive Pfade nachweislich andere oder defekte Semantik haben.

## P0: Korrektheitsblocker

### 1. Disk-Cache und frischer Backtest liefern nicht dieselbe Evaluation

`BacktestResult` enthält Per-Pair-/Monatswerte, Trade-Returns, Trades, Verlustserien und
Drawdown-Dauer (`evaluation/direct_backtester.py:28-76`). `to_dict()` lässt diese Felder aber weg
(`:78-99`). Der Disk-Cache rekonstruiert das Objekt genau aus diesem unvollständigen Dict
(`evaluation/cache.py:60-140`).

Folgen:

- frischer Backtest, RAM-Hit und Disk-Hit können verschiedene Fitness liefern;
- Cross-Pair-, Monatsstabilitäts-, Tail-Risk-, Clustering- und Monte-Carlo-Daten verschwinden;
- fehlende Daten werden später teilweise sogar besser bewertet als schlechte Daten.

Das blockiert jede belastbare Wiederholung und jeden automatischen Wave-Vergleich.

### 2. Mehrere Risiko-Penalties erhalten ihre Eingangsdaten nicht

`_backtest_result_to_metrics()` übernimmt unter anderem `avg_profit`, `avg_duration` und `trades`
nicht (`evaluation/fitness.py:1094-1138`). Die Duration-, Trade-Clustering- und
Spread-Aware-Penalties erwarten genau diese Felder (`:1597-1655`) und sind im normalen Pfad daher
weitgehend wirkungslos. Zusätzlich ist `avg_profit` bereits ein Verhältnis; der Spread-Code würde
es erneut durch 100 teilen.

### 3. Das prozentuale Standard-Holdout ist geleakt

Im Legacy-Runner läuft die Evolution auf dem vollen Timerange
(`run_ga.py:914-1035`). Erst danach werden Evolution- und Holdout-Range berechnet
(`:1085-1098`) und der bereits gesehene letzte Abschnitt erneut bewertet (`:1107-1128`). Das
berechnete `evolution_tr` wird vor der Evolution nicht gesetzt. Periodisches Holdout im
Standard-Core berechnet den Split ebenfalls, trainiert aber weiterhin auf dem Originalbereich
(`core/evolution.py:1361-1407`).

Historische Werte aus diesem Feature sind daher kein Out-of-Sample-Nachweis. Ein explizit
konfigurierter `holdout_test` kann disjunkt sein, prüft eine Überschneidung aber nicht zuverlässig.

### 4. NSGA-II verwirft neue Kinder vor ihrer ersten Bewertung

Environmental Selection wird direkt nach Erzeugung der unbewerteten Offspring aufgerufen
(`engine/generation.py:176-179`). Sie nimmt zuerst alle bewerteten Eltern; diese füllen bei einer
vollen Elternpopulation bereits das gesamte Budget. Unbewertete Kinder werden erst danach ergänzt
und passen nicht mehr hinein (`:764-811`). Praktisch friert die Evolution dadurch nach Generation 0
ein. Vorhandene isolierte NSGA-Hilfstests erkennen diesen Lifecycle-Fehler nicht.

**Follow-up 22.07.2026:** Dieser Lifecycle-Fehler ist repariert. `GenerationStep` liefert zunächst
reine Offspring; der GA evaluiert sie vollständig und führt danach `(μ+λ)`-Selection aus. Ein
Lifecycle-Regressionstest weist genetisch geänderte Kinder nach Generation 0 unter den Survivors
nach. Gleichzeitig wird `nsga2.min_trades` im Parallelpfad nicht mehr am Worker-Aufruf verloren.
Parallel-WF verwendet nun denselben per-Candidate-Evaluator wie Sequential statt einer semantisch
anderen Top-K-Nachbewertung. Diese Tests ersetzen keinen gepaarten OOS-Wirksamkeitsnachweis.

### 5. Beide Queue-Systeme sind aktuell unsicher

Der Python-Weg registriert beim `queue add` (`cli.py:268-291`). Der Scheduler startet den Child mit
derselben `--name`-ID (`orchestration/scheduler.py:96-132`), während der Child erneut registriert
(`cli.py:193-200`). Die Registry weist vorhandene IDs zurück (`orchestration/registry.py:114-118`).
Dieser Scheduler kann so keinen normal gequeueten Run starten.

Der Shell-Weg startet `python -m genetic_algorithm run` (`ga_auto_queue_v2.sh:392-397`), zählt zur
Slotbegrenzung aber nur Prozesse mit `run_ga.py` (`:332-336`, `:550-569`). Dadurch kann das
konfigurierte Parallelitätslimit überschritten werden.

### 6. Registry-Mutationen sind nicht transaktional

Read und Write einer Mutation sind getrennt (`orchestration/registry.py:114-119`, `:246-257`). Der
Read-Lock ist vor dem Write gelöst; der exklusive Lock liegt auf einer gemeinsam verwendeten
`.tmp`-Datei (`:259-284`). Ein isolierter Stresscheck in `/tmp` mit 60 parallelen Registrierungen
speicherte je Versuch nur einen Bruchteil der erfolgreichen Aufrufe und produzierte wiederholt
`FileNotFoundError`.

Eine kaputte JSON-Datei wird zudem als leere Registry interpretiert. Für parallele oder autonome
Waves ist das kein sicherer Zustandsspeicher.

### 7. Parallele Runs teilen und überschreiben Diagnostics

Der Standard-Core erzeugt `RunDiagnostics` unter einem globalen Outputpfad
(`config/schema.py:242-247`, `core/evolution.py:461-466`). Writer öffnen dieselbe
`generation_stats.csv` mit `w` und überschreiben dieselbe `run_metadata.json`
(`utils/run_diagnostics.py:176-200`, `:277-315`). Der Shell-Launcher setzt zwar `GA_OUTPUT_DIR`, der
Standard-Core berücksichtigt diese Variable aber nicht. Damit sind Artefakte nicht zuverlässig
einem Attempt zuordenbar und können sich gegenseitig beschädigen.

Status 23.07.2026: im kanonischen V2-Pfad behoben. Der hashgebundene
`AttemptOutputLayoutV2` setzt alle Standard-Engine- und Replay-Pfade absolut unter den Attempt,
isoliert auch DirectBacktester-Strategien, Freqtrade-Userdata und Backtest-Exports und enthält
relative Fallback-Writes durch ein attempt-lokales Arbeitsverzeichnis. `GA_OUTPUT_DIR` wird nicht
mehr als Produktionskonfiguration gelesen. Ein echter Mini-Evolutionslauf verifiziert, dass die
bekannten globalen Legacy-Pfade unverändert bleiben.

### 8. Es fehlt ein kanonischer, vollständiger Resultatvertrag

CLI und `run_ga.py` haben verschiedene Semantik. Der CLI-Pfad ruft nur `evolve()` auf und schreibt
wenige Registry-Felder (`cli.py:214-239`); der Legacy-Runner ergänzt Preflight, Strategieexport,
Robustheits-Postprocessing und Summary. Bei Island-Resultaten erhält die CLI ein Dict, behandelt es
aber wie ein einzelnes Individuum und registriert daher häufig Fitness und Profit als `0.0`.

Status 23.07.2026: für neue Ausführung behoben. Regime- und Generic-Island liefern eine vollständige
per-Island-Matrix mit einem gemeinsamen Replay-Rang. `IslandFinalistBatch` flacht alle Arme ab und
verweigert eine globale Rangliste ohne gemeinsame Panel-Provenienz, lokale Herkunft,
Deduplizierung, Sortierung sowie explizite Profit-/Trade-Messwerte. Der Coordinator reicht keine
beliebigen Backend-Dicts oder Listen mehr durch. Historische Nullwerte bleiben als
`LEGACY_IMPORT` klassifiziert und werden nicht rückwirkend als valide Messung umgedeutet.

Log-Parser holen Profit, Sharpe, Drawdown und Trades zudem als jeweils letztes Regex-Vorkommen; die
Werte müssen nicht zum selben Individuum gehören (`scripts/wave_comparison.py:87-173`). Ein früher
`EVOLUTION COMPLETE`-Text kann einen späteren Fehler verdecken.

Status 23.07.2026: im Entscheidungsweg behoben. `wave_comparison.py` akzeptiert nur den immutable
Resultat-Snapshot einer reconciled Wave und exakt eine daran gebundene ANALYSIS-Decision. Vor
Ausgabe rekonstruiert es die Analyse aus den erneut hashverifizierten Resultat-, Manifest-,
Kandidaten- und Szenarioartefakten und verlangt kanonische Gleichheit. Beliebige Logzeilen ändern
weder Analyse noch Vergleichshash. Das Monitoring liest aus Logs nur operativen Fortschritt;
Fitness/Profit werden nur aus `CANONICAL_V2` übernommen. Der alte Aggregate-Vergleich ist
fail-closed stillgelegt; der Legacy-Benchmark darf diagnostische Rohfelder zeigen, aber keine
Rankings, automatischen Schlussfolgerungen oder Vergleichscharts erzeugen.

### 9. Resume vertraute beschädigten oder inkompatiblen Checkpoints

Der Standard-Loader behandelte Checksumfehler nur als Warnung und las weiterhin V1/V2-Zustände.
Generic Island wählte Dateinamen lexikografisch, sodass beispielsweise Generation 9 neuer als
Generation 10 erscheinen konnte, und ordnete bei abweichenden Islandnamen Populationen nach Index
neu zu. Weder Config-, Code-, Daten- noch Genome-Schema-Identität waren verpflichtend.

Status 23.07.2026: Checkpoint V3 ist fail-closed. Eine kanonische Pflichtchecksumme wird vor jeder
Deserialisierung geprüft; legitime interne `NaN`-/`±inf`-Sentinelwerte werden explizit und
reversibel statt als ungültiges JSON kodiert. Resume verlangt exakte Hashes von resolved Config,
Code- und Datenmanifest, die Genome-Schemaversion, Engine-Typ und bei Islands die geordnete
Namensmenge. V1/V2, Diagnose-Snapshots ohne Provenienz, abweichende Populationen/Islands und
Checksumfehler werden abgelehnt. Generic Island wählt numerisch und fällt bei einem beschädigten
neuesten Checkpoint nicht auf ältere Evidenz zurück. 1.533 breite GA-Tests plus 188 relevante
Engine-/Coordinator-/Orchestration-Tests laufen grün; die drei bekannten falsch sammelbaren LLM-Dateien bleiben
unter `TEST-001` separat dokumentiert. Ein automatisches Scheduler-Recovery-Handoff aus einem
abgebrochenen Attempt bleibt bewusst außerhalb dieses Checkpoint-Kompatibilitätsfixes.

Warm-Start besaß dieselbe best-effort Schwäche sogar zweifach: Der Loader fing Quell-/Parsefehler
ab und lieferte eine leere Liste, anschließend fing `initialize_population()` erneut jede Ausnahme
ab. Fehlende explizite Pfade lösten außerdem eine globale mtime-basierte Suche aus; einzelne
ungültige Genome und HOF-Dateien wurden still übersprungen.

Status 23.07.2026: Ein aktivierter Legacy-Warm-Start ist atomar und content-addressed. Population
und HOF benötigen jeweils expliziten Pfad plus SHA-256 und das kanonische Genome-Schema. Es wird
keine Ersatzquelle entdeckt und kein Teilimport akzeptiert. Exakt die gehashten Bytes werden
geparst; fehlende/leere/manipulierte Quellen, ein ungültiges Genom, nichtfinite Fitness, ein
beschädigter interner V3-Checkpoint und unzureichende Population-Slots propagieren als fataler
Startfehler.

Status CFG-008 am 23.07.2026: Der semantische `strategy-gene-v2`-Validator prüft zusätzlich
Indicator-/Parameterfamilie, Operator, Condition-Referenz, endliche Werte sowie harte
Timeframe-/Risk-/ROI-/Trailing-/Regime-Grenzen. Der Migrator ist source-hashgebunden, atomar und
pro Genom berichtspflichtig; Warm-Start rekonstruiert aus der ebenfalls gehashten Legacy-Datei
Ziel und Report erneut. Der Scan von 11.708 vorhandenen Genomen fand 7.207 bereits exakte,
4.272 mindestens strukturell migrationsbedürftige sowie weitere semantisch beschädigte Einträge
(unter anderem falsche Parameterfamilien, `volume`, verwaiste IDs, ungültige CDL-Operatoren,
Trailing- und `between`-Fehler). Der globale HOF ist mit drei dokumentierten eindeutigen
RSI-Referenznormalisierungen migrierbar; der Wave-44-Top-30-Seed benötigt nur die neue
Schema-/Provenienzhülle. Fehlerhafte Archive werden nicht teilweise gerettet.

Status CFG-006 am 23.07.2026: Der V2-Runner löst eine Benutzer-Config genau einmal auf und
persistiert vor Queueing die vollständige `resolved_config.yaml` im Attempt-Root. Der
kanonische semantische Hash ist Teil des Manifests; der exakte Datei-Hash ist Teil der
geschlossenen Worker-Inputmatrix und ihres Bindings. Worker und Child-Wave-Handoff prüfen diese
Kette erneut und lesen die mutable Quelle nicht mehr. Ein Regressionstest verändert nach dem
Queueing gezielt eine gleichnamige historische Config unter `config/done`; der Attempt bleibt an
seinen Snapshot gebunden. Eine Veränderung des Snapshots wird vor Ausführung beziehungsweise als
verifiziertes `INVALID_RESULT` erkannt.

Status CFG-007 am 23.07.2026: Der zuvor zentral aufgerufene Legacy-Validator enthielt zwei
verschiedene AP-Regelsätze und las darin teilweise veraltete Pfade. Einzelne historische Runs
wurden zu widersprüchlichen „sicheren“ Grenzen hochgerechnet: Standardpopulation höchstens 15,
Inselpopulation gleichzeitig höchstens 6 oder mindestens 60 und höchstens zwei Pairs. Diese
wirtschaftlichen Behauptungen sind kein ausführbarer Vertrag mehr. `ga-config-invariants-v1`
erzwingt ausschließlich mechanische Grenzen und eindeutige Semantik; Tuningparameter werden über
gepaarte Seeds, identische Panels und Budgets als Planner-Hypothesen geprüft. Resolver,
Compatibility-API und Editor-Hook verwenden dieselben Regeln. Der Repo-weite Config-Scan fand
außerdem zehn historische Classic-Island+WF-Dateien, deren WF-Flag von der Engine nachweislich
deaktiviert wurde. Sie sind unter `DATA-009` als falsch klassifizierte Evidenz festgehalten.

## P1: Fachliche Bewertungsfehler

### Additive Fitness kann Verluste kompensieren

Bei den Standardgrenzen entspricht bereits 0 % Profit einem normalisierten Profitwert von 0,5.
Eine negative Strategie verliert nur Bonusverstärkung, wird aber nicht unzulässig
(`evaluation/fitness.py:1180-1299`, `:1337-1344`). Gute oder fehlende Risiko-/Winrate-Werte können
Verluste kompensieren. Ein Penalty-Floor rettet Mehrfachverletzer zusätzlich auf mindestens 10 %
der Ausgangsfitness (`:1657-1663`).

Optimierungsrang und absolute Deployability müssen deshalb getrennt werden.

### Fehlende Risikodaten wirken gut oder neutral

Fehlende Drawdown-Dauer und fehlende Verlustserie ergeben perfekte Teilwerte. Fehlende Monats- und
Pairdaten ergeben neutrale 0,5 (`evaluation/fitness.py:1225-1256`). Unvollständige Telemetrie darf
nie einen Vorteil erzeugen; Pflichtfelder müssen fail-closed sein.

### Tradefrequenz ist zeit- und kontextblind

Die Fitness bewertet absolute Trades statt Trades pro aktivem Monat, Pair oder Kapitaleinsatz. Die
als „kürzeste“ dokumentierte Timeframe wird über den kleinsten Multiplikator gewählt und ist damit
faktisch die längste (`evaluation/fitness.py:110-170`). Explizite Schwellen werden entgegen dem
Kommentar weiterhin nach Pairzahl skaliert. Die Gaussian-Funktion fällt bei hoher Aktivität wieder
ab, obwohl Kosten, Turnover und Kapazität separat gemessen werden sollten (`:1395-1428`).

### Winrate ist überbewertet, wenn Payoff und Tail-Risk fehlen

Eine hohe Trefferquote sagt ohne durchschnittlichen Gewinn, durchschnittlichen Verlust,
Expectancy und Tail-Loss wenig aus. Wave 44 demonstriert das praktisch: Champions mit ungefähr
90-94 % Train-Winrate verloren sämtlich auf dem jeweils ausgelassenen Pair.

### Sharpe, Sortino und DSR sind nicht auf einer kanonischen Equity-Serie aufgebaut

Der lokale Freqtrade-Pfad kombiniert Kalenderdauer und Streuung einzelner Trades
(`freqtrade/data/metrics.py:336-394`), nicht eine kalendergerichtete tägliche Portfolio-Return-Serie.
DSR verwendet diesen Wert mit `n_returns = num_trades`, obwohl Skew/Kurtosis nicht zuverlässig
geliefert werden (`validation/deflated_sharpe.py:41-162`, `evaluation/fitness.py:1351-1371`). Die
DSR-Trial-Historie ist außerdem reihenfolge-, Worker- und Identitätsfeld-abhängig.

### Per-Pair- und Monatsprofit sind keine Portfolio-Returns

Sie werden als Summe einzelner `profit_ratio`-Werte gebildet
(`evaluation/direct_backtester.py:824-855`). Stakes, überlappende Positionen und Compounding fehlen.
Die Werte sind nützliche Diagnostik, aber keine kapitalgewichtete Portfoliorendite.

### Deferred Pair-Validation erzeugt unvergleichbare Kandidaten

Unvalidierte Kandidaten erhalten pauschal ungefähr 92 % ihrer Train-Fitness
(`evaluation/fitness.py:478-499`). Nur Top-N werden später vollständig validiert (`:591-632`). Wenn
diese durch echte schlechte Validation fallen, können nie validierte Kandidaten darüber stehen und
weiter selektiert werden. Zusätzlich bleiben angezeigte Primary Metrics Train-Werte, während die
Fitness composite ist. Räumliche Pair-Validation wird in `holdout_*`-Felder geschrieben und damit
mit zeitlichem Holdout vermischt.

Pairs ohne Trades fehlen aus dem `groupby`; eine Strategie mit Trades auf nur einem von fünf Pairs
kann deshalb wie ein Single-Pair-Resultat neutral bewertet werden.

### Parallel und sequenziell sind nicht semantisch gleich

`nsga2_min_trades` wird in Parallel-Tasks gespeichert, aber nicht an den Worker übergeben
(`evaluation/parallel.py:1474-1507`). Parallel-WF und sequenzielles WF unterscheiden sich zudem bei
Gap-Penalty, Fehlerfällen, Drawdown und Success-Ratio. Gleiche Config und gleicher Seed können daher
einen anderen Algorithmus ausführen.

### Fee-Noise ist nicht reproduzierbar

Die Seedbildung nutzt Pythons pro Prozess randomisierten `hash()` und einen generationsabhängigen
Strategienamen (`evaluation/direct_backtester.py:1027-1041`). Identische ausführbare Phänotypen
können je Prozess, Generation und Worker andere Kosten erhalten. Der Cache bildet diese Zufälligkeit
nicht sauber ab.

### Regime-Auswertung kann schlechte Segmente entfernen

Fehlgeschlagene und Low-Trade-Segmente werden vor der Aggregation entfernt. Der Harmonic Mean
entfernt Nullwerte zusätzlich (`market/regime_aware.py:385-496`). Komplettes Versagen in schwierigen
Regimen darf die Gesamtbewertung nicht verbessern.

### Surrogate kann ungeprüfte Schätzungen als echte Fitness einsetzen

Es gibt kein Mindest-R² zur Aktivierung; nahe verwandte Nachkommen werden zufällig in Train/Val
geteilt, und übersprungene Kandidaten erhalten endgültige Surrogate-Fitness
(`evaluation/surrogate.py:216-357`). Die optionale Mutation liefert ein neues Objekt, der Caller
ignoriert jedoch die `skipped`-Liste (`core/evolution.py:1013-1023`). Surrogate-Kandidaten dürfen
ohne echten Backtest weder HOF noch Promotion erreichen.

### Follow-up 22.07.2026: Config- und Side-Vertrag repariert

Der Foundation-Branch schließt mehrere konkrete Mechanikfehler, ohne daraus bereits einen
Wirksamkeitsnachweis abzuleiten:

- NSGA-II verwendet ausschließlich `mode: nsga2` und `nsga2.objectives` mit `name/type/scale`.
  Der frühere Scheinmodus und wirkungslose Objective-Keys werden vor Start abgelehnt. Die bisher
  konstante `trade_frequency`-Objective liest nun explizit `num_trades`; fehlende Metriken werden
  nicht mehr als Null behandelt.
- Generic-Island-Rotation übergibt `random_seed` statt des vom GA ignorierten `seed`. Verschiedene
  Inseln erhalten dadurch nachweislich verschiedene Runtime-Seeds.
- Die Surrogate-Filterung liest `genetic_algorithm.mutation_rate`, ersetzt nach Mutation das
  tatsächliche Populationsgenom, löscht stale Evaluation und prognostiziert den neuen Phänotyp
  erneut. Nicht prognostizierbare Genome gehen fail-open zum echten Backtest. Ein persistierter
  Evidenzstatus trennt Schätzung, erfolgreichen/gescheiterten Backtest und unbekannte Legacy-
  Herkunft. HOF, finale Runner-Resultate, Holdout-/CPCV-Auswahl, V2-Shortlist und Candidate-Export
  akzeptieren nur `BACKTEST_VALID`; historische Surrogate-HOF-Einträge werden ignoriert.
- Das Modell lernt auf deduplizierter Raw-Fitness, nicht auf populationsabhängiger Fitness-
  Sharing-Fitness. Aktivierung verlangt ausreichend Samples und ein konfigurierbares Mindest-R²
  auf vollständig neueren GA-Generationen; ein zufälliger Sibling-Split genügt nicht. Nach
  Checkpoint-Restore muss Modell und Gate neu aufgebaut werden. Das schließt die mechanische
  Validitätslücke, beweist aber keinen inkrementellen Blind-OOS-Nutzen; `safe_v2` lässt das Feature
  weiterhin aus.
- Unabhängige Short-Conditions werden nicht mehr aus Long-Templates kopiert. Generator und
  Mutation modellieren bullish/bearish explizit pro Side; Short-Entry ist bearish und Short-Exit
  bullish. Candlestick-Patterns und neutrale ATR/ADX-/Aktivitätsfilter besitzen eigene Tests.
- Der Regime-Aggregator persistiert jedes erwartete Segment mit explizitem Outcome und Coverage.
  Failed-, ungültige, Null- und Low-Trade-Segmente verschwinden weder aus Mean/Min/CVaR noch aus
  dem Harmonic Mean. Positive Fitness ohne ausreichende Trades wird auf null gekappt, Verluste
  bleiben erhalten und fehlende Evidenz erzeugt konservativen Worst-DD. `exclusive` kann keine
  Regime mehr nur in der Bewertung ausblenden, solange es die Runtime-Strategie nicht filtert.
- Fitness besitzt nun eine deterministische Panel-ID aus Datenbereich/Pairs, Kosten, Scoring-
  Policy, Evaluatortyp und Regime-Segmentmenge. Standard-HOFs sind panelgebunden. Ohne
  content-addressed Datenmanifest sind sie zusätzlich run-lokal, weil gleiche Config keine
  unveränderten Candle-Dateien beweist.
- Generic- und Regime-Islands schreiben lokale Search-Fitness nicht mehr in die Shared-HOF und
  sortieren sie nicht mehr als globale Finalisten. Top-K je Insel wird phänotypisch dedupliziert
  und auf einem gemeinsamen Base-Pair- beziehungsweise neutralen Union-of-Regimes-Panel replayed;
  nur erfolgreiche `COMMON_REPLAY`-Resultate erreichen HOF und Runner. Specialist-Boost ist im
  Vergleich ausgeschaltet. Fehlendes Replay ist fail-closed statt Local-Raw-Fallback.
- Der zuvor global genutzte Generic-Parallel-Evaluator ignorierte Pair-Subsets und semantische
  Insel-Overrides. Er wird jetzt nur geteilt, wenn alle Panel-IDs identisch sind. Cross-Panel-
  Tournament, Merge und External-Export verwenden keine fremden Raw-Skalen mehr, sondern
  bidirektionale Reevaluation beziehungsweise round-robin Local-Ranks.

Der vollständige Config-Scan umfasst 461 YAMLs, 17 NSGA-Konfigurationen und 65 Objective-Einträge;
alle gefundenen NSGA-Configs bestehen den zentralen Vertrag. Der GA-Testlauf besteht mit 1.457
Tests und 13 bekannten Warnungen, wobei `test_llm_providers.py` und
`test_llm_strategy_generation.py` wegen ihrer bereits bekannten fehlenden Fixtures separat
ausgeschlossen sind. Diese Ergebnisse belegen Konfigurations- und
Ausführungssemantik, nicht zusätzlichen OOS-Profit.

## Robustheitsfeatures: aktueller Nutzwert

| Feature | Urteil | Grund und nächste Form |
|---|---|---|
| Pair-Validation | **Behalten, reparieren** | Passt zum Transferziel und hält Validation-Pairs aus der Trainingsfitness. Benötigt zweistufige Selektion, Zero-Trade-Coverage, Pair-Rotation/LOPO und getrennte Felder. |
| Prozent-Holdout | **Stoppen** | Aktuell geleakt. Später nur disjunkt, unveränderlich und genau einmal als finaler Test. |
| Walk-forward | **Umbenennen/redesignen** | Keine Reoptimierung: ein fixes Gene wird je Fenster bewertet. Parallel und Sequential verwenden inzwischen denselben Evaluator; Routing-Priorität, überlappende Fenster und hoher Rechenaufwand bleiben. Als budgetbegrenzte, geblockte Temporal-Validation auf Top-K denkbar. |
| Monte Carlo | **Aus Fitness entfernen** | Trade-Reihenfolge ändert den finalen Compound-Return mathematisch nicht; kein belastbarer DD/Ruin-Test. Neu als Block-Bootstrap plus ausschließlich ungünstige Kostenstress-Szenarien. |
| CPCV/PBO | **Nicht als CPCV bezeichnen** | Purge/Embargo werden im Validator nicht benutzt; bereits selektierte Top-K werden nur auf Blöcken nachbewertet. Optional als Block-Rank-Diagnostik. |
| DSR | **Deaktivieren** | Falsche Return-/Sample-Semantik und orderabhängige Trialzählung. Erst nach Referenztests auf Daily Returns neu bewerten. |
| Param-Sensitivity | **Neu bauen** | Aktuell ohne Produktions-Caller; Rundung, Bool/Int, Nullwerte, Bounds und Interaktionen sind fehlerhaft. |
| Surrogate | **Mechanisch abgesichert, deaktiviert** | Schätzungen sind als Search-only-Evidenz markiert und von HOF/Finale/V2-Export ausgeschlossen; Aktivierung verlangt Generation-OOS-R². Ein gepaarter Blind-OOS-Nachweis für eingesparte Backtests bei gleicher oder besserer Finalqualität fehlt weiterhin. |
| NSGA-II | **Mechanisch repariert, weiter experimentell** | Offspring werden vor `(μ+λ)` evaluiert und Parallel/Sequential sind vertraglich gleich. Aktivierung erst nach gepaarten Blind-OOS-Runs gegen Single-Objective-Control. |
| Regime-Aware | **Mechanisch repariert, weiter experimentell** | Segment-Coverage und Aggregation sind fail-closed. Qualität der Detektion, Panelwahl und inkrementeller Blind-OOS-Nutzen sind weiterhin unbewiesen. |
| MAP-Elites/AOS | **Experimentell stoppen** | MAP-Elites sucht teils nicht gelieferte Felder; AOS-Mutationsauswahl ist im produktiven Pfad nicht verdrahtet. |
| SIS | **Standardmäßig aus** | Keine belastbare positive Wirkung; Suchraum-/Configfehler und schlechte Predictor-Güte. Nur als gepaarter Experimentalarm. |

## SIS-Befund

SIS scheitert derzeit nicht an einer einzelnen Stellschraube, sondern an Daten-, Integrations- und
Experimentdesignfehlern.

- Configs schreiben `immigrants_max_fraction` und `immigrants_per_generation`; der Integrator liest
  `max_immigrants_fraction` und `immigrants_per_gen`.
- `GenerationStep` cappt externe SIS-Immigrants auf `genetic_algorithm.random_immigrants`, während
  SIS-Logs die vom Provider erzeugte höhere Zahl melden.
- Das „full profile“ überschreibt Timeframes außerhalb der Config und tauscht Indicator-Typen, ohne
  deren Parameter neu zu erzeugen. Vorhandene Artefakte enthalten zum Beispiel BBANDS mit
  Ichimoku-Parametern und CCI mit MACD-Parametern sowie 15m/1h-Immigrants in 4h-Experimenten.
- Der Weight-Credit ist assoziativ, nicht kausal: wiederholte Elites und alle Komponenten eines Genes
  erhalten denselben Credit. Dadurch entsteht ein selbstverstärkender Feedback-Loop.
- Der Corpus mischt Fitnessversionen, Pairsets, Zeiträume und Timeframes, dedupliziert globale
  Phänotypen und verliert Wiederholungsmessungen/Kontext.
- Sieben von acht vorhandenen Regressionsmodellen haben negatives OOS-R². Der Profit-Classifier hat
  AUC 0,682, aber F1 0,059. Die Health-Anzeige misst überwiegend Daten-/Artefaktvorhandensein, nicht
  bewiesenen OOS-Nutzen.

Ein sauber gepaartes E/F-Beispiel mit Seed 42, gleichem 4h-Suchraum, 6x8 Population und 15
Generationen spricht gegen die aktuelle SIS-Version:

| Arm | HOF Fitness max/mean | Validation-Profit mean | Positive Validation-Einträge | DD mean | Validation-DD mean |
|---|---:|---:|---:|---:|---:|
| Control | 0,459 / 0,396 | +0,82 % | 24/30 | 0,0084 | 0,0133 |
| SIS | 0,378 / 0,343 | -1,20 % | 9/25 | 0,0106 | 0,0277 |

Ein Seed ist keine Signifikanz, aber dies ist klare negative Evidenz für genau diese Version. Andere
SIS-Läufe sind durch ungleiche Horizonte, unvollständige Arme oder illegale Suchräume nicht als
Wirksamkeitsnachweis geeignet.

### Wave 44

Alle vier gespeicherten Champions waren auf fünf Trainingspairs profitabel und verloren auf dem

Nach dem Ziel „hoher Profit bei geringer Wahrscheinlichkeit großer Verluste“ dürfte keiner dieser

### Detaillierte Ergebnisreports

In 137 `results_detailed_*.json`-Dateien waren 19 leer. Die übrigen enthielten 537 Rangzeilen:

- 387 `SAFE`, 23 `WARNING`, 20 `OVERFIT`, 107 `UNKNOWN`
- 116 von 387 `SAFE`-Zeilen hatten Primary-Profit <= 0
- 230 von 387 `SAFE`-Zeilen hatten Holdout-Profit <= 0
- 84 Dateien enthielten doppelte Individual-IDs in ihren Toplisten; insgesamt 161 zusätzliche
  Duplikatzeilen

`SAFE` bedeutet damit im aktuellen Report nur geringe relative Degradation, nicht positive
Ökonomie oder Deployability. Eine Verluststrategie, die auf „Holdout“ weniger stark verliert, kann
als sicher erscheinen.

### Registry

Die Registry enthielt zum Auditzeitpunkt 56 Einträge: 42 `completed`, 8 `running`, 6 `failed`. Von
42 abgeschlossenen Einträgen hatten 35 `best_profit <= 0`; viele davon sind durch den Island-Dict-
Extraktionsfehler als Null gespeichert, vier Werte sind tatsächlich negativ. Mindestens die
Wave-44-Statuszeilen sind trotz vorhandener Abschlussartefakte nicht reconciled. Wave-45-Artefakte
wurden wegen des extern laufenden/unklar sichtbaren Zustands nur gelesen und nicht verändert.

### Strategy-Corpus

`strategy_corpus.parquet` enthält 6.848 Zeilen und 117 Spalten. Die Datenlage ist für globale
Parameterbeweise ungeeignet:

- Profit/Sharpe/DD/Winrate/Trades: 6.687 nicht-null
- Holdout-/Validation-Profit: nur 2.185 nicht-null
- Verlustserie und DD-Dauer: nur 458 nicht-null

- 2.520 Zeilen ohne Wave, 2.669 ohne verwertbare Origin, 4.314 ohne Train-/Validation-Pair-Kontext
- 4.061 Zeilen haben positive Fitness bei Profit <= 0

- im obersten Fitness-Dezil ist nur ein Primary-Profit nicht positiv, der Median-Profit liegt aber
  nur bei ungefähr 0,096 %; Zeiträume, Kosten und Kontexte sind nicht normalisiert

Timeframe-Unterschiede im Corpus sind stark wellen-/config-konfundiert. Sie dürfen nicht als Beweis
interpretiert werden, dass 4h pauschal besser oder 5m pauschal schlechter ist.

## Feature- und Parameterhinweise: was wirklich belegt ist

Kein Indicator und kein GA-Parameter ist derzeit kausal als überlegen bewiesen. Gründe sind
wechselnde Fitnessformeln, selektierte/verwandte HOF-Samples, fehlende Provenienz, geleaktes
Holdout, ungültige Config-Experimente und zu wenige gepaarte Seeds.

Innerhalb von `run_id` kontrollierte Beobachtungen liefern lediglich Kandidaten für neue A/B-Tests:

| Kandidat | Deskriptiver Befund | Einordnung |
|---|---|---|
| MACD | medianes Val-Profit-Delta +2,28 Punkte in 27 Runs; 81,5 % positiv | mild upweight testen |
| ROC | +1,29 in 20 Runs; 75 % positiv | mild upweight testen |
| CDL_HAMMER | +1,22 in 18 Runs; 77,8 % positiv | mild upweight testen |
| BBANDS | +0,875 in 34 Runs; 70,6 % positiv | mild upweight testen |
| PSAR | Val-Median -1,235; nur 14,3 % von 21 Runs positiv | downweight testen |
| KAMA, TEMA, VROC | negative Validation-Mediane | downweight testen |
| CCI | global stark angereichert, innerhalb Run medianes Fitnessdelta -0,0042 | klares Konfundierungsbeispiel; statisches 3x-Gewicht nicht belegt |

ADX, BBANDS und RSI zeigen kleine positive In-Run-Fitnessdeltas, aber praktisch keine relevante
ökonomische Profitwirkung. Stoploss- und ROI-Korrelationen brechen auf Validation nahezu vollständig
zusammen. Daraus darf kein bestimmter Stoploss-/ROI-Wert abgeleitet werden.

Diese Kandidaten gehören in gepaarte, budgetgleiche Experimente, nicht direkt in eine automatische
Policy.

## Weitere konkrete Codeprobleme

Der statische Undefined-Name-Check fand potenzielle Runtime-Fehler in experimentellen/teilweise
aktiven Pfaden:

- `advanced/coevolution.py`: `StrategyGene`
- `advanced/incremental.py`: `Population`
- `core/island_model.py`: `pd`
- `market/regime_aware.py`: `DatasetPolicy` und `detector`
- `run_ga.py`: `logger`

Außerdem enthalten `scripts/benchmark_report.py`-Mappings doppelte Keys. Vor Aktivierung der
jeweiligen Features müssen Reachability-Tests klären, welche Pfade tatsächlich betroffen sind.

## Schlussfolgerung

Der Kern kann Strategien erzeugen und viele Hilfsfunktionen sind unit-getestet. Die derzeitige
End-to-End-Pipeline kann aber nicht garantieren, dass zwei Scores dasselbe bedeuten, dass ein
„Holdout“ ungesehen war, dass ein Queuezustand stimmt oder dass eine hohe Fitness eine wirtschaftlich
positive, risikoarme Strategie bezeichnet.

Die nächste sinnvolle Entwicklungsarbeit ist daher keine weitere Wave-Konfiguration, sondern ein
kleiner, verifizierter Mess- und Ausführungskern. Auf diesem Kern kann die gewünschte Automation dann
deterministisch und nachvollziehbar aufgebaut werden.
